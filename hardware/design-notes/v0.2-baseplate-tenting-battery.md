# v0.2 Modular Baseplate — Tenting + 18650 Battery Bay (corrected)

Status: **v0.2 conceptual + partially-verified parametric CAD.** Corrects
the v0.1 pass, which the user rejected: "atrocious... square and dont match
the footprint." Companion OpenSCAD sources live in
[../cad/v0.2/](../cad/v0.2/); read that folder's README for render
instructions. This is still an iterative pass, not a fabrication-ready
design.

## What was wrong with v0.1

v0.1's `baseplate_tray.scad` built the new baseplate from `cube([W, D, H])`
sized to each mesh's raw XY bounding box — i.e. a flat rectangular box. A
real photo of the printed case (`Misc/CASES.webp`) shows the actual
TylerDactyl case is a sculpted, organic, per-finger-column stepped/curved
shape, with a spherical trackball cutout on the right half — nothing like a
flat rectangular tray. v0.1 is moved to
[../cad/v0.1-deprecated/](../cad/v0.1-deprecated/) and must not be used.

## What was actually measured this pass (numpy-stl + OpenSCAD, both real)

- **CASE and PLATE share the same X/Y coordinate frame per half.** Measured
  independently, the bounding boxes match exactly:
  - LEFT: X `-65.39..84.98`, Y `-100.07..47.19` (both CASE and PLATE).
  - RIGHT: X `-116.90..65.39`, Y `-110.62..47.19` (both CASE and PLATE).
  - Z origin between files is **still not confirmed shared** — CASE Z
    ranges `3.0..70.4` (L) / `3.0..65.5` (R) in each file's own frame, PLATE
    Z ranges are offset differently; do not trust cross-file Z stack-up.
- **PLATE is a uniform ~3.0mm flat sheet** (both halves) — sampled a 6×6 XY
  grid of vertex Z values across each plate; top/bottom Z is flat almost
  everywhere, confirming PLATE really is just the organic-outlined switch
  plate, not a contoured part.
- **CASE bottom is NOT a simple flat rim.** Sampled all mesh vertices within
  1.5mm of each CASE's minimum Z and printed their XY spread: low points
  are scattered across nearly the entire footprint (roughly the full
  `-28..+56` X range and `-90..+45` Y range sampled for the left half, not
  confined to a narrow perimeter band). This means the case's bottom
  surface is genuinely contoured/stepped, matching the photo — **a flat
  baseplate top face will only touch the case at its lowest points and gap
  elsewhere.**
- **The CASE meshes are not closed/manifold.** OpenSCAD's own CGAL boolean
  engine confirms this directly:
  ```
  ERROR: The given mesh is not closed! Unable to convert to CGAL_Nef_Polyhedron.
  ```
  reproduced for both `21.05.01 CASE LEFT.stl` and `21.05.02 CASE
RIGHT.stl` when attempting a trivial `intersection()` against a bounding
  box. **This means real 3D boolean CSG (difference/union/intersection)
  against the CASE meshes is not usable in OpenSCAD in this pass.**
- **The PLATE meshes ARE closed/manifold** — the same boolean test against
  `21.05.04 PLATE LEFT.stl` and `21.05.06 PLATE RIGHT.stl` succeeded (~3s
  each). So 3D CSG against PLATE would work, but PLATE is just the flat
  switch plate — its shape doesn't tell us the CASE's real bottom contour.
- **`projection()` works on the CASE meshes despite being non-manifold.**
  It doesn't route through CGAL_Nef_Polyhedron the way 3D booleans do, so
  it succeeds (~2s) and gives a trustworthy real 2D outline. This is the
  basis for the v0.2 approach below.

## v0.2 approach: outline-extrude, not box, not raw-mesh-boolean

`hardware/cad/v0.2/`:

1. `lib/organic_outline.scad` — `projection(cut=false)` of the real CASE
   STL → a true 2D silhouette of the actual organic footprint.
2. `lib/organic_tray.scad` — `linear_extrude()`s that real outline into an
   open-top tray (thin floor + wall ring at real wall thickness), then adds
   the battery pocket, corner posts, and controller shelf as ordinary
   primitive CSG (cylinders/cubes/spheres) — never a boolean against the
   mesh itself.
3. `baseplate_left.scad` / `baseplate_right.scad` — assemble the above per
   half with placeholder battery/controller positions.
4. `fit_check_left.scad` / `fit_check_right.scad` — preview-only (`%`)
   overlay of the real CASE + PLATE solids for visual alignment sanity
   checks (not exportable/renderable geometry).

**Both `baseplate_left.scad` and `baseplate_right.scad` were test-rendered
to STL in this pass and succeeded** (valid closed solids, no CGAL/manifold
errors) — confirming the plan-view outline now really is the organic case
shape, not a bounding-box rectangle.

## What this does NOT solve (explicit limitation)

The new tray's **top face is still flat** (a planar `linear_extrude`). Per
the measured finding above, the real CASE bottom rim is contoured, not
flat — so this v0.2 tray's outline is correct in plan view (X/Y) but its
mating surface will still only contact the real case at a few low points,
not flush-seal all the way around. Working directly with the imported CASE
mesh in 3D to get a true contoured mating face is not usable in OpenSCAD in
this pass, because the mesh is not closed and 3D boolean CSG against it
fails outright (reproduced above, not a guess).

**What a human needs to do about this in a real CAD tool** (Fusion 360 /
FreeCAD, both of which have proper solid-healing/mesh-repair pipelines
OpenSCAD lacks):

1. Import `21.05.01 CASE LEFT.stl` / `21.05.02 CASE RIGHT.stl` and run mesh
   repair / stitch-and-heal (FreeCAD: Mesh Design → Analyze/Repair; Fusion:
   Mesh → Modify → Reduce/Repair, or the "Remesh" utility) to produce a
   closed/manifold solid.
2. Once closed, either: (a) take a thin "cap" slice of the bottom few mm of
   the healed solid and use that as the actual contoured baseplate mating
   surface (extend it downward for the battery bay / walls), or (b) offset
   the healed solid's bottom surface outward by the wall thickness to
   generate a shell that naturally follows the real contour.
3. Re-derive real corner/screw-boss positions from the healed solid (mesh
   forensics on raw triangle soup, which was explicitly not attempted in
   this OpenSCAD-only pass, becomes tractable with a real CAD kernel's
   feature-recognition tools).
4. Re-run the shim-based tenting mechanism concept (see v0.1 notes,
   mechanism still sound in principle: flat horizontal mating faces at
   every joint, only shim height changes) against the real contoured
   contact points once known — the risk flagged in the task ("shim blocks
   may not contact evenly") is real and unresolved here; it needs the
   actual contour data from step 1–2 before shim height math can be
   trusted.

## Option A: regenerate from Cosmos instead/in addition

Because this keyboard's case was originally generated by Cosmos (a
parametric generator with a native tenting-angle input), regenerating
directly from the saved Cosmos configs (`Misc/COSMOS.txt` links) at a
higher tenting angle may be **much lower-risk than retrofitting a baseplate
onto the existing organic mesh** — Cosmos would presumably produce an
already-correct, already-manifold, already-tented case in one step, instead
of us reverse-engineering contour/mating data from an unhealed mesh.

Recommended: open each `ryanis.cool/cosmos/beta#cf:...` link yourself,
re-export the case at the same hand-scan/key-layout config but with a
tenting parameter in the 8–20° range, and compare the result against the
organic-mesh-retrofit path above. This was not something I could safely do
myself in this pass (no reliable interactive browser tool), so it's
recorded here as a parallel option rather than attempted.

   confirm the pocket doesn't breach a thin section before trusting it.

   OpenSCAD preview.

   not a measurement — `BATTERY_POS`/`CONTROLLER_POS` in
   `baseplate_right.scad` were pushed away from the case's approximate
   center based on where the photo shows the trackball, nothing more
